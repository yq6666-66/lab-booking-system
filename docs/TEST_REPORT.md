## 一、实验环境与边界

- 本机 Windows x64，服务仅监听 `127.0.0.1` 回环地址，每轮实验使用独立临时端口与全新数据库副本。
- 并发实验为固定请求数实验，非长时间压测：1、5、10、20 个并发用户各 20 轮，共 **720 次预约请求**；每轮以线程屏障对齐后同时申请同一空闲场次。
- 中断实验为受控故障注入：测试版程序在指定 `request_id` 的请求处理过程中主动终止进程，共 **20 次**（两类中断点各 10 次），仅针对测试脚本启动的测试进程。
- p50/p95/max 为客户端测量（含连接与线程调度开销），只描述本机本条件，不代表生产容量。
- **工具链限制（如实说明）**：本机 MinGW-w64 GCC 15.2 发行版不含 libasan/libubsan 运行库（已核实无 `libasan.a` 可链接），ASan/UBSan 动态内存检查不可用。替代方案为 `gcc -fanalyzer` 静态分析（第三节）、绑定参数类型静态核查（第四节）与加固构建运行验证（第八节）。

## 三、静态分析

`scripts/build.ps1 -Analyze` 以 `gcc -fanalyzer` 编译全部自有源码（`src/*.c`、`tests/unit.c`），配合 `-Wall -Wextra -Wformat=2 -Wshadow -Wstrict-prototypes`：**零告警**。开发过程中该配置曾拦截并推动修复一处格式截断告警与两处缩进误导告警。

## 四、绑定参数类型静态核查

在 `db_run/db_rows/db_first/db_num` 的调用中，SQL 占位符个数与格式串（`i`=整数、`s`=文本）必须逐一对应，错位会把整数当指针解引用并导致进程崩溃。本轮新增脚本对所有调用做自动核查：提取 SQL 的 `?` 数量与格式串比对，并按参数形态（字符串字面量 / `now_sec()` / `x.id` / 常量）交叉验证类型。

核查范围：`src/service.c`、`src/http.c`、`src/db.c`、`src/util.c`、`tests/unit.c`，**74 处带绑定参数的调用全部匹配**。该手段在本轮开发中先后定位出两处真实缺陷（`sessions_list` 的查询格式串、`/api/slots` 的格式串漏位），均已修复并补充回归用例。

## 六、签到与爽约专项实验

**T22** 用 `--checkin-window 1 --sweep-interval 1` 构造确定性场景：用户甲预约后场次进入签到窗口，甲未签到；乙已候补。扫描线程在窗口结束后于单个 `BEGIN IMMEDIATE` 事务内完成：甲预约 → `CANCELLED` 且 `cancel_reason='NO_SHOW'`；乙由 `WAITING` → `PROMOTED` 并新建 `source='WAITLIST'` 的 `CONFIRMED` 预约；向甲写入 `NO_SHOW` 通知、向乙写入 `PROMOTED` 通知；该场次有效占用恒为 1。

**设计要点（本轮修复）**：补位产生的预约若沿用"场次开始时间 + 窗口"判定，会立即再次满足超时条件而陷入反复释放。现改为：`source='WAITLIST'` 的预约以其**补位时刻**作为签到起点，扫描条件与签到接口校验使用同一规则，因此补位后既不会被立即回收，也仍保有完整签到时间。该缺陷由 T22 首次运行时暴露并修复。

## 七、数据模型升级与迁移验证

schema 由 v1 升至 v2：`reservations` 追加 `checked_in_at` 与 `cancel_reason`，`sessions` 追加 `created_at`，新增 `notifications` 表与其索引；`db_check` 增加四条不变式（已签到者必须仍为 CONFIRMED、爽约标记必须伴随 CANCELLED 且未签到、取消原因非空时必须为 CANCELLED、有取消时间者必须有取消原因）。

迁移策略为**按列存在性幂等追加**，不重建表：用 Python 构造一个带数据的 v1 库（含一条历史取消记录、无 `cancel_reason` 列），交由新版程序 `--check` 打开后验证：`user_version` 1→2、三个新列齐全、`notifications` 表建立、历史取消记录回填 `cancel_reason='USER'`、`users`/`slots` 行数不变、完整性检查通过。既有演示库可原地升级，无需重新初始化。

## 八、加固构建运行验证

`scripts/build.ps1 -Harden` 以 `_FORTIFY_SOURCE=3`、`-fstack-protector-strong`、`-ftrivial-auto-var-init=zero`、`-fno-strict-overflow` 重新构建全部程序（`*-harden.exe`）后，单元测试与完整实验全部通过。该组合用于在无 ASan 运行库的条件下提供运行时内存安全防线，覆盖范围弱于完整 sanitizer，报告中不夸大其效力。
