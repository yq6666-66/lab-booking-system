## 2. 架构与请求生命周期

五层：浏览器（原生 JS，无框架）→ CivetWeb 接入（8 工作线程，会话/CSRF/Origin/Host 校验、16KB 体限制）→ 业务层 service.c（全部写路径在单写者事务内）→ 数据访问 db.c（参数绑定、语句 LRU 缓存、线程连接复用、幂等迁移）→ SQLite（WAL + synchronous=FULL）。

一次写请求的生命周期（预约为例）：

```
POST /api/reservations
→ 接入层：会话认证 → CSRF → Origin → 请求体解析（拒重复键）
→ booking()（service.c:156，约 240 行的核心函数）：
   BEGIN IMMEDIATE            ← 取得写锁，并发写从此串行化
   → 用户可用性（enabled/爽约受限/时间重叠）
   → 幂等回执查询（同编号同参数→重放原结果；异参数→409 冲突）
   → 容量校验（CONFIRMED+HELD < capacity）
   → [审批实验室] 落 PENDING（不占容量）
   → [满员+高优先级] 抢占：选未签到且 priority 更低者 → CANCELLED/PREEMPTED + 信用补偿 + 通知
   → 资源声明校验（BR12：归属/AVAILABLE/同时段配额）
   → INSERT 预约（source=DIRECT）
   → request_receipts 落回执
   COMMIT                     ← 任一步失败整体 ROLLBACK
→ 响应 JSON 封套 {code, message, data}
```

取消路径在同一事务内执行 `promote_fill`（service.c:131）：循环递补至满员或队列空。

## 3. 核心机制深挖（答辩重点）

### 3.1 并发一致性：为什么 720 次争抢零超卖
- **单写者事务协议**：所有写操作用 `BEGIN IMMEDIATE` 起手——事务开始即排队写锁，并发写转化为串行化；事务内"读容量→校验→写"不存在检查与写入之间的竞态窗口。
- 容量为 1 的场次在 1/5/10/20 并发 × 20 轮共 720 次争抢中，每轮成功预约数与数据库占用数恒为 1（实验样本内未出现超卖）；其余全部收到明确 409，无忙碌失败。
- v1 曾用部分唯一索引兜底，容量制后改为完全依赖事务协议——正确性从"数据库约束兜底"演进为"事务协议保证"，这是论文 4.4.1 的核心论证。

### 3.2 幂等回执：网络重试安全
- 每个写操作携带客户端生成的 UUID 请求编号；服务端把（用户，编号）→（动作，参数摘要，HTTP 状态，结果 JSON）与业务变更**同事务**持久化。
- 同编号同参数 → 重放原结果（含 409）；异参数 → 409 REQUEST_ID_CONFLICT；5xx 不落回执可安全重试。以"至少一次提交 + 服务端幂等"替代脆弱的"恰好一次"。
- 30 次故障注入（提交前 86 / 提交后 87 / 扫描中 88 三类 × 各 10 轮）全部正确恢复：未提交整体回滚、已提交完整保留、重启后首次重试完成剩余业务。

### 3.3 候补三档策略（BR19，r24/r26 演进——最大创新点）
递补扫描共用一套"可执行性"框架（停用者 SKIPPED、时间冲突暂跳保留序号），差异在**候选排序**：

| 档 | 排序 | 语义 |
|---|---|---|
| strict | `priority DESC, id`，队首冲突即阻塞 | 公平绝对但名额空置 |
| executable（默认） | 同上，队首冲突**暂跳**继续扫描 | 名额不空置 |
| weighted（r26） | score 降序：**1000×优先级 + 200×(信用−5) + 60×log₂(1+等待小时)** | 老化消除同档饿死 |

评分量纲设计（答辩必问）：等待每翻倍 +60 分；同优先级下 1 点信用差（200 分）≈ 8 小时等待可追平；管理员基准 1000 分不被任何普通用户的老化越级——**老化只解决"同档饿死"，不侵蚀角色与信用激励**。

矩阵实验（`tests/experiment.py --matrix`，三策略 × ρ=0.7/1.0/1.3/1.6，确定性场景）：strict 在队首冲突时空置率 100%；executable/weighted 均满额递补且**平均等待 7.2ks → 3.6ks（weighted 减半）**；Jain 公平指数三档一致（0.73–0.82）。实现在 `promote()`（service.c:66）。

### 3.4 知情候补：转正概率（r26）
- `GET /api/suggestions` 逐场次返回 bookable/joinable + 原因码（满员/配额/冲突/信用/提前期），并附 `queue_ahead`（排位）与 `promote_probability`。
- 概率算法（`promote_probability()`，service.c:1415）：同实验室**同星期几**过去 35 天（5 周）已开场场次中，"释放名额数 ≥ 排位"的场次占比；释放 = CANCELLED(USER/NO_SHOW/REJECTED) + EXPIRED。**样本 <5 场返回 null（不下结论）**——经验分布的诚实口径。
- 评估与提交之间允许竞态，提交仍由事务内全量校验兜底（建议不削弱正确性）。

### 3.5 公平性审计（r26）
- `GET /api/admin/fairness?days=` （`fairness_admin()`，service.c:1528）：按用户聚合候补入队/转正/退出/跳过/平均等待秒（转正时刻−入队时刻，经 promoted_reservation_id JOIN，零迁移）；全站 **Jain 公平指数 = (Σx)²/(n·Σx²)**，x = 窗口内该用户获得预约数，1 为完全公平。
- 每日候补上限 `--waitlist-daily-limit`（409 WAITLIST_LIMIT，北京日界重置）补全防刷。

### 3.6 预约七态状态机与组合语义
PENDING（待审批，不占容）→ CONFIRMED ⇄ HELD（限时保留，占容）→ 签到/签退；终态 CANCELLED（原因四分 USER/NO_SHOW/REJECTED/PREEMPTED）、EXPIRED、候补 SKIPPED。
**占容口径 = CONFIRMED + HELD**。五条组合语义基准（CONTRACT「语义澄清」节，T63–T67 钉死）：
1. PENDING 不占容量，批准时事务内重校（409 APPROVAL_CAPACITY）；
2. 抢占仅限未签到且 priority 更低者，+1 信用补偿（钳 0..5）；
3. 候补递补是系统行为，**不经过审批**（审批实验室的递补直接 CONFIRMED/HELD）；
4. 维护中资源拒绝新声明，既有声明与预约保留；
5. 改期不重计周配额，本周有效预约总数守恒。

### 3.7 资源一体化（BR12/17/18/21）
预约可声明 ≤5 项资源：同一事务内校验归属 → AVAILABLE → 同时段声明数 < total（BR12）；可配按星期+时刻的可用时段窗（BR17）；维护工单开=MAINTENANCE 拒新声明、关=恢复（BR18）；可开"需资格"开关，未持资格 409 QUALIFICATION_REQUIRED（BR21）。

### 3.8 安全设计
- 口令 Argon2id（libsodium）；会话令牌仅存 SHA-256 摘要，HttpOnly+SameSite=Strict Cookie；全 POST 强制 CSRF + Origin + Host 三重校验。
- **凭据生命周期（r25）**：停用/改密/重置密码在同一事务内吊销全部 API 令牌（db_check 有"停用用户无令牌"不变量）；`--restore` 恢复旧备份会重新激活吊销前凭据——已记录为运维边界。
- 防爆破（5 次失败锁 900s）与令牌桶限速；登录对不存在用户名做**哑哈希**，有效/无效账号响应时间比 1.07（显著降低枚举可观测差异，实验口径）。
- 全响应 CSP/nosniff/XFO/Referrer-Policy；16KB 体限制拒重复键。

## 6. 高频答辩问题预答

**Q1 为什么用 C，不用 Java/Python？**
贴近系统底层、资源与错误显式管理，能完整展现从 HTTP 报文到磁盘字节的全链路；在无 GC、无重型框架的约束下保证正确性，对工程纪律与测试体系要求更高，方法与结论更具普适价值。CivetWeb/SQLite 证明嵌入式组件可低成本构建完整 Web 服务。

**Q2 并发下怎么保证不超卖？**
单写者事务协议：BEGIN IMMEDIATE 使写事务串行化，容量校验与写入同事务无竞态窗口；720 次争抢实验 + 每轮超容量落库检查双重验证；30 次故障注入证明崩溃不破坏不变量。

**Q3 为什么不用 Redis/消息队列/微服务？**
单机单库场景下 SQLite WAL 已满足读写需求（混合负载 p99 <100ms）；引入外部组件破坏"零依赖单文件部署"；业务拆分会破坏"取消—递补—通知"同事务原子性（负收益，已书面评估）。

**Q4 崩溃/断电怎么办？**
WAL + synchronous=FULL 保证掉电持久；未提交事务整体回滚、已提交完整保留；kill -9 后重启首次重试完成剩余业务（30 次注入实验覆盖三类中断点）；在线备份用 SQLite Backup API，--restore 恢复后自动 integrity_check。

**Q5 weighted 的公式怎么定的？**
三项量纲制衡：优先级 1000 保证管理员不被越级；信用 200 使 1 点信用差约需 8 小时等待追平（激励守约）；等待按 log₂ 对数加速——翻倍才 +60，久等者稳态反超但不至于压过信用结构。对照实验显示同量名额下平均等待减半。

**Q6 转正概率可信吗？**
经验分布而非模型：同实验室同星期过去 5 周的真实释放记录，样本不足 5 场明确返回 null 不给数字；只作建议，提交时事务全量校验兜底。

**Q7 Jain 指数是什么？为什么用它？**
公平性标准度量 (Σx)²/(n·Σx²)∈(0,1]：所有人获得相同资源时为 1。矩阵实验中三策略 Jain 一致（名额总数相同、归属不同），说明策略改变的是"给谁"而非"给多少"——这正是等待时长数据补足的维度。

**Q8 遇到最难的 bug？**
讲第 10 例：int 实参经变参按 8 字节读取是未定义行为——星期参数高 32 位是调用现场残留，概率查询随机返回空集，两轮全量回归偶现后才用最小复现+调试桩定位。教训：变参接口的所有实参必须显式宽化；UB 不等于立刻崩溃。（备选：weighted 静默退化例——测试断言必须与既有默认行为可区分。）

**Q9 为什么回环部署、没有 HTTPS？**
目标场景是实验室单机管理 + 本机/局域网浏览器访问，回环是天然安全边界（防外部扫描）；TLS 证书体系已预留（CivetWeb 裁剪 NO_SSL 可恢复），列为部署化扩展而非课设范围。

**Q10 系统能支撑多大规模？**
写路径受 SQLite 单写者约束（同槽写约 200 rps、跨槽约 140–210 rps），适合百人级实验室；读路径经连接复用+语句缓存达 1,900+ rps。混合负载零 5xx、p99<100ms。再往上需分片或换存储引擎（论文展望已述）。

**Q11 工作量证明？**
80+ 提交、26 轮迭代、16 版 CHANGELOG、2,900 行 C + 5,600 行测试、CONTRACT 34KB 逐端点契约、11 个被测试先行暴露并固化的真实缺陷（论文 6.9 节逐例记录）。

**Q12 测试怎么保证没漏？**
五层互补：单元（业务直调）→ 集成（真实进程+真实 HTTP，74 组含并发/故障/组合语义）→ 契约（49 端点形状+14 错误）→ 灰盒/文档/vendor 供应链一致性 → 模糊/浸泡/E2E；CI 三通道含 ASan 内存安全；所有"性能提升 X%"均有 benchmark 脚本与原始证据归档（docs/evidence/）。
