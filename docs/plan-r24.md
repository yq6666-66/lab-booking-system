## 一、差距分析（文档建议 × 本项目现状）

| 文档建议 | 本项目现状 | 定性 | 处置 |
| --- | --- | --- | --- |
| **可执行 FIFO**（队首临时冲突则暂跳、保留原序号） | 纯 FIFO + 优先级，队首冲突会**阻塞整条队列** | **实质缺陷**（会造成名额空置） | **本轮实现** |
| **HELD 限时保留**（递补后需确认，超时回收） | 补位**直接生效**，不确认 | **机制缺失**（用户不知情即被占地，也可能错过） | **本轮实现** |

| 资格授权表（qualifications） | 无（仅账号 `enabled`） | 功能缺失 | **本轮实现** |
| outbox（外部通知） | 仅站内通知，无外部渠道 | 缺扩展点 | **本轮实现**（渠道插件化 + outbox 表） |
| 可注入时钟 | `now_sec()` 全局直调 | 可测试性不足 | **本轮实现** |
| 模块化目录（booking/waitlist/storage/…） | `service.c` 单文件 | 可维护性不足 | **本轮拆分** |
| 对照实验（严格 FIFO vs 可执行 FIFO） | 无 | **论文核心实证缺失** | **本轮实现** |

## 二、实施清单（按优先级）

### P0-1 可执行 FIFO（文档 6.1）

- **现状**：`promote_fill()` 取 `ORDER BY priority DESC,id LIMIT 1`，若该用户的候补因**时间冲突**（已预约重叠时段）不可执行，则**整条队列阻塞**，名额空置。
- **方案**：把"取队首"改为**顺序扫描**：按 `priority DESC,id` 遍历 WAITING，对每个候选判定
  1. 账号启用（永久无效 → 置 `SKIPPED`）；
  2. 与该用户已有确认预约**无时间重叠**（临时冲突 → **保留原序号，继续看下一个**）；
  3. 通过则递补，继续扫描直到容量用尽。
- **公平边界**：暂跳者**保留原序号**（不改 `id`/`priority`），故下次扫描仍优先于后来的申请 → "可执行申请间的 FIFO"。
- **预期效果**：名额空置率下降（论文可测）；`SKIPPED` 与暂跳原因可审计。
- **适用场景**：多实验室、用户同时段冲突率高的真实排课。
- **实施前提**：需在事务内逐候选重查时间冲突（O(n) 次查询，n 为队列长度，规模小可接受）。

### P0-2 HELD 限时保留（文档 5.1/5.2）

- **现状**：补位即 `CONFIRMED`，用户无确认机会。
- **方案**：新增 `HELD` 态（`reservations.status` CHECK 扩展）+ `hold_deadline` 列；
  递补时写 `HELD`，`hold_deadline = min(now + 确认窗口, 时段开始时刻)`；用户 `POST /api/reservations/{id}/confirm` 转 `CONFIRMED`；
  扫描器把 `now >= hold_deadline` 的 HELD 转 `EXPIRED` 并**重新递补**（形成自然的重试环）。
- **HELD 占容量**（与文档一致），`EXPIRED` 不占。
- **预期效果**：用户知情、可拒绝；超时自动回收并让给下一位。
- **适用场景**：需要用户确认的实验设备预约。
- **实施前提**：`capacity` 统计口径需同时覆盖 `CONFIRMED` 与 `HELD`（否则会超售）——这是本轮最易出错处。

### P1-3 资格授权（qualifications）

- **方案**：`qualifications(user_id, asset_id, granted_at, expires_at, note)`；资源声明时若该资源配置了资格要求（`assets.requires_qualification`），则未持有效资格者 409 `QUALIFICATION_REQUIRED`。
- **预期效果**：贵重设备需培训授权，贴合真实实验室管理。
- **适用场景**：分级设备准入。

### P1-4 可注入时钟

- **方案**：新增 `clock_now()`（默认取系统时间），`booking`/`sweep`/`credit` 路径改用它；测试可用环境变量或 `--fake-now` 注入固定时刻，验证 `hold_deadline` 边界。
- **预期效果**：截止时刻边界可确定性测试（不依赖真实等待）。
- **适用场景**：所有涉及时间的断言。

### P2-5 拆分 `service.c`

- **方案**：拆为 `booking.c`（预约/候补/审批）、`asset.c`（资源/时段/维护/资格）、`stats.c`（统计/导出）、`token.c`（令牌/信用）。共享 `app.h` 与 `db` 访问层，行为不变。
- **预期效果**：可维护性、可测试性；与论文"软件工程"维度呼应。

### P2-6 通知渠道插件化 + outbox

- **方案**：`notify()` 内部维护渠道表（函数指针），内置 `inbox`（站内，现状）；可选 `file` 渠道（写文件，演示出站）。同事务写 `outbox` 表，提交后派发，失败可重试。
- **预期效果**：加渠道零改核心；为"外部通知"留可演示的落点（不引入网络依赖）。

### P3-7 对照实验（严格 FIFO vs 可执行 FIFO）

- **方案**：新增 `tests/experiment.py`，用**同一组申请序列**分别跑两种策略（通过 `--waitlist-strategy=strict|executable` 开关切换），统计：名额利用率、候补成功率、等待时间中位数/P95、暂跳次数。
- **预期效果**：论文的核心实证数据，且能诚实报告公平性代价。

## 四、明确不做（附理由）

- **合并 reservations/waitlist 为单表**：本项目分表已形成 47 端点契约与 61 项断言，合并属高风险重构，收益主要是"设计更优雅"，对课题目标（候补闭环 + 一致性验证）无实质提升。
- **外部通知网络出站（SMTP/Webhook）**：与既有取舍一致，不做重出站依赖。
- **确定性虚拟时钟 + 事件回放实验框架**：成本高，本轮用真实服务 + 短窗口参数完成对照实验即可。

## 五、兼容性约束（硬性，逐项自检）

外部文档是**建议性说明**，不代表已实现任何内容；本轮所有改动都必须在**不破坏现有工程**的前提下落地。五条硬约束：

1. **接口兼容**：47 个既有端点的路径、请求体、响应形状不变；新端点只做加法。
2. **断言兼容**：61 项既有集成断言的语义不得修改。若某项新机制**必然改变**既有行为，该机制必须**默认关闭**并提供显式开关。
3. **数据兼容**：老库（schema v4）可幂等迁移到 v5，迁移失败不得损坏数据；`main.c` 的 `user_version` 上限同步放宽。
4. **结构兼容**：不引入第三方库；`web/` 保持无框架原生 JS；模块拆分只调整文件组织，**不改函数签名与调用契约**。
5. **默认行为兼容**：改进型机制在原有场景下行为一致；改变语义的机制默认关闭。

### 逐项兼容性判定

| 改动 | 是否影响既有行为 | 处置 |
| --- | --- | --- |
| 可执行 FIFO | 仅"队首临时冲突"场景结果不同（该场景既有断言未覆盖，属**缺陷修复**） | 默认启用；提供 `--waitlist-strategy=strict` 回退，同时服务对照实验 |

| 可注入时钟 | 默认取系统时间 | 完全兼容 |
| 拆分 `service.c` | 函数签名与行为不变 | 完全兼容 |
