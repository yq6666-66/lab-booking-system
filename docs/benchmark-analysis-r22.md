# 同类开源项目对标分析与优化建议（r22 调研）

> 调研对象：GitHub 上与「实验室资源管理与预约候补一体化系统」相关的开源项目
> 分析维度：资源管理、预约机制、候补排队、并发处理
> 对照基线：本项目 v1.11.0（C11 + CivetWeb + SQLite + cJSON + libsodium；39 契约端点 / 55 集成断言 / 24 单元测试）
> 说明：本文件为调研产物，**未纳入版本库**，供论文"相关工作/选型对比"章节与后续迭代取舍使用。

## 二、四个维度的设计特色

### 2.1 资源管理

| 项目 | 核心做法 | 可借鉴点 |
| --- | --- | --- |
| LibreBooking | 资源（Resource）为一等实体，支持**资源层级/分组**、每资源独立日程与配额；**quotas + credits 双机制**控制滥用 | 配额与信用**统一成一个可累加的账户模型**，而非两套独立规则 |
| Easy!Appointments | **服务（Service）× 服务提供者（Provider）** 二维建模；Provider 有 **working plans**（自身的可工作时间段） | 「资源自身也有可用时段」，与「场次开放时段」解耦 |
| classroombookings | **房间 + 日课表（period）+ 学年 timetable** 三层；学期切换不丢历史 | 时段模板可配置，且**版本化**（新学年复制而非覆盖） |
| 本项目 | `labs → slots → assets`；容量制场次 + 资源声明配额 + 每周配额 | 已有三维建模，但**资源没有自己的可用时段**，时段结构硬编码为一小时 |

**本项目现状**：资源（`assets`）只有 `total`（数量）与 `status`（可用/维修/停用），预约时以 `asset_claims` 声明占用，并受"同时段配额"（BR12）约束。资源与场次是**间接耦合**（资源属于实验室，场次也属于实验室）。

### 2.2 预约机制

| 项目 | 做法 |
| --- | --- |
| LibreBooking | 支持**一次预约多个资源**、周期预约、ICS 订阅（Outlook/Thunderbird）；预约经 `ReservationHandler` 统一处理，写路径用 `SELECT ... FOR UPDATE` |
| Easy!Appointments | **booking rules**：提前量、缓冲期、最短/最长时长、取消截止时间 |
| classroombookings | 预约按"日课表格子"落位，冲突即不可选（UI 层直接禁用） |
| 本项目 | 固定 1 小时场次、容量制（`capacity` 1..200）、提前量（BR14）、周期发布（weekdays 掩码 + 开放时段）、改期、备注、审批流 |

**本项目现状**：单场次预约（一个预约 = 一个 slot），已有提前量/周期/改期/审批，**缺少跨时段连续预约与取消截止时间**。

### 2.3 候补排队（本轮差距最大处）

| 项目 | 做法 | 特色 |
| --- | --- | --- |
| **Smart-Resource-Allocation** | **优先级预约 + 抢占式调度**：高优先级预约可**抢占**低优先级；冲突者自动入候补；用 `heapq` 维护优先队列 | **唯一实现"优先级 + 抢占"的样本**，最贴近真实教学场景（教师/课程 vs 学生自由预约） |
| LibreBooking | waitlist 为独立领域对象（`Domain/ReservationWaitlistRequest.php`）；**后台 Job（`Jobs/sendwaitlist.php`）** 定时扫描并推送候选通知 | 候补与通知**解耦为后台任务**（与本项目 `sweeper` 思路一致） |
| 票务类项目 | FIFO 队列 + 取消即自动提升队首 | 标准做法，与本项目一致 |
| 本项目 | **纯 FIFO**：`waitlist` 表 + 取消/爽约时按 `id` 升序取队首有效候补补位 + 双向通知；无效账号跳过、停用实验室阻止新候补 | FIFO 公平性已闭环，但**无法表达"这门课的学生优先"** |

**结论**：本项目候补的**公平性与一致性已达同类上限**（FIFO + 跳过无效 + 事务内补位），但**策略维度单一**。引入优先级/抢占是与成熟平台的**唯一实质差距**，也是论文中最容易讲出"设计取舍"的一处。

### 2.4 并发处理

| 项目 | 做法 | 评价 |
| --- | --- | --- |
| LibreBooking（MySQL） | 关键写路径 `SELECT ... FOR UPDATE` 悲观锁；库存式表结构 | 依赖数据库行锁，代码中锁的使用点很少（全仓库仅 1 处） |
| 票务类 | 事务 + 唯一约束兜底 | 常见 |
| **本项目（SQLite）** | **`BEGIN IMMEDIATE` 串行化写事务 + 局部唯一索引**（每 slot 一个 CONFIRMED / 每 (user,slot) 一个 WAITING）+ WAL + `busy_timeout=3000` + 重试 + 请求回执去重 | **更简洁且更强**：靠"唯一索引 + 立即写事务"在**数据库层**杜绝超卖，无需显式行锁；并有 720 次并发争抢实测（每轮恰好 1 个成功）与故障注入验证 |

**结论**：**本项目并发处理优于同类开源实现**（尤其是可验证性：并发实验 + 故障注入 + 完整性门禁）。这一项不必对标改进，反而可作为论文的**技术亮点**与"为什么选 SQLite 而非 MySQL"的论据。

## 三、针对本项目的优化建议

每项给出：**借鉴来源 → 现状 → 改进方案 → 预期效果 → 适用场景**。
优先级：P0 契合课题主线且能讲出设计取舍；P1 显著提升实用度；P2 体验/工程；P3 架构演进。

### P0-1 候补优先级与抢占（对标 Smart-Resource-Allocation）

- **现状**：`waitlist` 纯 FIFO（`ORDER BY id`），所有用户候补权平等。
- **方案**：
  1. `waitlist` 增加 `priority INTEGER NOT NULL DEFAULT 0`（迁移走 `has_column` 幂等块）；补位排序改为 `ORDER BY priority DESC, id ASC` —— **高优先级内仍 FIFO，公平性不被破坏**。
  2. 优先级来源：`labs.require_approval` 同类思路，实验室可配 `priority_roles`（如 ADMIN/教师账号优先级 10，普通学生 0）；预约请求可带 `priority_hint`（服务端按角色校准，**不接受客户端自报优先级**）。
  3. **抢占**（可选开关 `--preempt-enabled`）：高优先级预约在容量已满时，可将**优先级更低且尚未签到**的确认预约转为 `CANCELLED + PREEMPTED`，并向被抢占者写通知与**信用补偿**（不记爽约）。
- **预期效果**：候补从"先到先得"升级为"**策略可配的公平**"；抢占引入状态机新转移（`CONFIRMED → CANCELLED/PREEMPTED`），可在论文中讨论**公平性 vs 效率**的取舍。
- **适用场景**：实验室承担教学任务（课程排课优先级高于个人自由预约）、贵重设备向科研团队倾斜。

### P0-2 配额与信用统一为「信用账户」（对标 LibreBooking quotas + credits）

- **现状**：**两套独立机制**——每周配额（BR13，按次数）+ 爽约信用（BR10，近 7 天爽约 ≥2 受限）。用户需要同时理解两个规则。
- **方案**：引入 `users.credit`（或独立 `credit_ledger` 流水表），把所有约束折算为**一个账户**：
  - 预约成功 `-1`；按时签到 `+1`（净零）；爽约 `-2`；被抢占 `+1`（补偿）；管理员发放加分。
  - 每周配额改为"**信用下限 + 每周回补**"（如每周一恢复至 5，低于 0 时禁止新预约）。
  - 保留 `credit_ledger` 流水（时间、变动、原因、关联预约），使每一次扣减**可追溯**。
- **预期效果**：规则从"两条并列"变为"**一条可解释的账本**"，管理端可展示信用走势；为后续引入"信用换优先权"（P0-1 的升级）留出接口。
- **适用场景**：需要长期引导用户守约（爽约治理），且希望规则对用户透明。

### P0-3 资源自身的可用时段（对标 Easy!Appointments working plans）

- **现状**：`assets` 只有 `status` 三态；资源维护期只能整资源停用，**无法表达"每周三下午检修"**。
- **方案**：新增 `asset_windows(asset_id, weekday_mask, start_minute, end_minute, reason)`（幂等迁移），在 `booking()` 的声明校验阶段增加一条：**声明的资源在其自身时段内必须可用**；资源页签可维护时段。
- **预期效果**：资源从"静态清单"升级为"**有时段语义的可调度对象**"，与场次时段正交，贴近真实设备管理。
- **适用场景**：贵重仪器分时开放、设备定期保养窗口。

### P1-4 ICS 日历**订阅**（双向，对标 LibreBooking）

- **现状**：只有 `GET /api/me/calendar/export`（一次性下载），用户每次都要重新导出。
- **方案**：新增 `GET /api/me/calendar.ics?token=<API 令牌>`，**复用 r22 落地的 X-API-Token 只读认证**（令牌在 URL 上，因此该端点需豁免 Cookie、仅校验令牌、且限流）。返回 `text/calendar` 长缓存头。
- **预期效果**：Outlook/系统日历**一次性订阅、自动刷新**；与 r22 的令牌能力形成闭环，是"令牌只读访问"的最佳落地场景。
- **适用场景**：用户希望预约自动出现在手机日历；避免反复登录查看。

### P1-5 跨时段连续预约（对标 LibreBooking 多资源/长时段预约）

- **现状**：一个预约恰好占用一个 1 小时 slot；2 小时实验需下两次单，可能被抢走一半。
- **方案**：`POST /api/reservations` 接受 `slot_ids: [...]`（或 `duration_slots: n`），在**同一事务**内校验全部时段容量与资源配额，**全成或全败**；`request_receipts` 的 `payload_digest` 覆盖数组内容以防重放变形。
- **预期效果**：长时段预约**原子化**，消除"订到一半"的尴尬；事务边界不变（仍是 `BEGIN IMMEDIATE`），不破坏既有并发正确性。
- **适用场景**：2-3 小时的实验课、设备调试、需要连续占用的场景。

### P1-6 资源维护工单（对标 equipcare / Project KNOT 的维护跟踪）

- **现状**：`assets.status` 可手工置为 `MAINTENANCE`，但**没有维护记录**（谁改的、为什么、多久）。
- **方案**：`asset_maintenance(asset_id, started_at, ended_at, reason, operator_id)`；资源置为维修时**必须**开一条工单，恢复时关闭；可与 P0-3 的时段联动（维修期自动屏蔽可选时段）。
- **预期效果**：设备全生命周期可追溯，为论文提供"资源管理闭环"的完整叙事。
- **适用场景**：报修—维修—复用的日常流程。

### P2-7 管理端资源占用周视图（对标 resourcenest / RoomBooking）

- **现状**：管理端只有表格（`admin.html` 列表）与统计柱状图（纯 SVG）。
- **方案**：新增「占用日历」页签，**纯前端 SVG** 绘制"实验室 × 时段"周视图格子，数据来自已有的 `/api/slots` + `/api/admin/records`（**零后端改动、零依赖**）。
- **预期效果**：占用冲突与空闲时段一眼可见，排课效率显著提升。
- **适用场景**：管理员协调多个实验室的排课。

### P2-8 时段模板可配置（对标 classroombookings 的日课表）

- **现状**：`publish_slots` 硬编码 08-12 / 14-18，每场 1 小时，午休固定。
- **方案**：`POST /api/admin/slots/publish` 增加可选 `periods`（如 `"08:00-09:35,09:50-11:25,13:30-15:05"`），服务端解析为时段模板；不传则保持现状（**向后兼容**）。
- **预期效果**：适配不同学校的作息（单节课 45/90/95 分钟不一），系统从"某校定制"变为"可配置"。
- **适用场景**：跨学院/跨学校部署。

### P3-9 插件化通知渠道（对标 LibreBooking plugin-ready）

- **现状**：通知只落库（站内信），渠道单一。
- **方案**：定义渠道扩展点（函数指针表：`struct notify_channel { const char *name; int (*send)(...); }`），内置 `inbox` 渠道，可注册 `webhook` / `wecom` 等；`notify()` 遍历渠道表。
- **预期效果**：接入企业微信/钉钉只需加一个文件，核心零改动；是"架构可扩展性"的论文素材。
- **适用场景**：真实部署时需要外部通知。

### P3-10 拆分 `service.c`（对标 LibreBooking 的分层）

- **现状**：`src/service.c` **993 行**，承载预约/候补/审批/令牌/资源/统计全部业务，违反单一职责。
- **方案**：按领域拆为 `booking.c`（预约与候补）、`asset.c`（资源与声明）、`stats.c`（统计与导出）、`token.c`（令牌），共享 `app.h` 的 `Result` 封装与 `db.h` 的数据访问层。
- **预期效果**：可维护性、可测试性提升；与 r22 引入的"契约测试分层"呼应，在论文"软件工程"维度更站得住。
- **适用场景**：长期演进（本轮不做，避免大范围重构影响验收）。

## 四、差距总结

| 维度 | 本项目 | 成熟平台（LibreBooking 等） | 差距定性 |
| --- | --- | --- | --- |
| 资源管理 | 三维建模（lab/slot/asset）+ 声明配额 | 资源层级 + 资源自身时段 + 维护工单 | **中等**（缺时段与工单） |
| 预约机制 | 容量制 + 提前量 + 周期 + 改期 + 审批 | 多资源/长时段 + 取消截止 + ICS 订阅 | **小-中** |
| 候补排队 | FIFO + 跳过无效 + 事务内补位 + 双向通知 | **优先级 + 抢占** + 后台 Job | **机制维度单一**（最大差距） |
| 并发处理 | **`BEGIN IMMEDIATE` + 唯一索引 + 回执去重 + 实测验证** | MySQL 行锁（`FOR UPDATE`），实测证据少 | **本项目更优**（可作亮点） |
| 用量报表 | 内外双口径利用率 + CSV 导出 | 细粒度 usage reporting | 基本持平 |
| 架构 | 单文件 `service.c`、硬编码路由 | Domain/Application/WebService 分层、插件化 | **中等**（工程性） |

## 五、如果只做三项

按"契合课题主线（资源管理 + 预约候补一体化）× 能讲出设计取舍 × 增量可控"排序：

1. **P0-1 候补优先级与抢占** —— 唯一能补齐"候补"维度实质差距的机制，且天然引出公平性讨论。
2. **P0-2 信用账户统一** —— 把已有两条规则收敛为一条可解释的账本，改动集中在 `users`/`waitlist` 相关路径，风险可控。
3. **P1-4 ICS 订阅** —— 复用刚落地的 X-API-Token，投入小、演示效果好（手机日历直接看到预约）。

> 不建议本轮做：P3-9 插件化、P3-10 拆分 `service.c`（重构面大、验收风险高，适合答辩后或独立一轮）；Webhook/SMTP 出站能力（与既有取舍"不做重出站依赖"一致）。
