高校开放实验室的一站式资源管理平台——**预约、候补、签到、审批、信用、公平审计**全闭环，纯 C 实现。

> **技术核心**：单写者事务保证并发零超卖 · 持久化回执实现幂等重试 · 故障注入验证崩溃恢复 · 三档候补策略（含老化加权）· Jain 公平指数量化治理

## 技术栈

**后端为纯 C11 单体服务，前端为零依赖原生三件套，全部第三方源码 vendor 入库并 SHA256 锁定——克隆即构建，构建即可运行，部署三件套（exe + DLL + web/）即可迁移。**

| 层 | 选型 | 要点 |
|---|---|---|
| 语言标准 | **C11**（约 3,300 行自研代码） | 纯 C 单体，无解释器、无 GC、无运行时依赖；`-Wall -Wextra` 零告警，`-fanalyzer` 静态分析门禁 |
| HTTP 服务 | **CivetWeb**（嵌入式，commit 588860e） | 8 工作线程，静态资源与 API 同进程服务，仅监听回环地址；全响应下发五条安全头（CSP / nosniff / DENY / no-referrer / Permissions-Policy） |
| 数据库 | **SQLite 3.53**（WAL + synchronous=FULL） | 单文件库、17 张表；容量/唯一性等业务不变量由局部唯一索引在库层兜底；schema v5 版本化幂等迁移（旧库无损升级，构造旧库实测验证） |
| JSON | **cJSON 1.7** | 严格解析（重复键拒绝）；请求体 16 KB 上限，超限 413 |
| 密码学 | **libsodium 1.0** | Argon2id 口令哈希（哑哈希将账号枚举时序差压至约 3%）；CSPRNG 生成会话令牌/盐；服务端仅存哈希 |
| 并发正确性 | 自研**单写者事务协议** | 全部业务写走 `BEGIN IMMEDIATE` 短事务 + 持久化请求回执（同编号幂等重放）；720 并发争抢零超卖、30 次故障注入恢复全部正确——均为可复现实验实证 |
| 前端 | **原生 HTML / CSS / JavaScript**（约 800 行脚本 + 850 行样式） | 无框架、无构建步骤、无 CDN；严格 CSP `default-src 'self'` 下全站零内联脚本/样式；ui.js 共用基座 + theme.js 深色主题（View Transitions 过渡） |
| 可观测性 | 自研 metrics 模块 | Prometheus 文本格式 `/metrics`（请求计数器 + 延迟直方图累积 bucket），标准运维生态直接抓取 |
| 测试 | **Unity** + Python 标准库 + **Playwright** | 25 单元（链接业务层直调，不经 HTTP）/ 79 集成断言组 / 56 端点契约 / 8 E2E 浏览器用例；测试客户端仅用 Python 标准库，零第三方依赖 |
| CI/CD | **GitHub Actions 四通道** | 构建与集成测试 / 契约与文档一致性 / gcc `-fanalyzer` 静态分析 / llvm-mingw AddressSanitizer 内存安全（Windows） |
| 供应链安全 | vendor 源码入库 + SHA256 锁定 | [dependencies.lock.json](docs/dependencies.lock.json) 固定版本与哈希；依赖获取脚本仅访问白名单域名并核对校验和 |

各组件的版本、许可证与仓库链接明细见文末[第三方组件](#第三方组件)表。

## 核心技术（自研）

依赖选型之外，本项目自研的关键技术按域归纳：

### 并发与一致性

| 技术 | 说明 |
|---|---|
| 单写者事务协议 | 全部业务写走 `BEGIN IMMEDIATE` 短事务，写锁争用按 `busy_timeout` 退避——**720 并发争抢实验零超卖**（1/5/10/20 并发 × 20 轮） |
| 持久化请求回执 | `(user, request_id)` 唯一约束：同编号同参数重放返回原结果、换参数 409——网络故障后安全重试，终态结果不重复执行 |
| 故障注入验证 | `TEST_FAULTS` 构建内置三个确定性崩溃点（提交前退出 86 / 提交后响应前退出 87 / 扫描中途退出 88），**30 次中断-恢复实验全部正确** |
| 库层不变量兜底 | 局部唯一索引承载"每场次一个 CONFIRMED""每(用户,场次)一个 WAITING"等容量不变量——应用层缺陷也会被数据库拒绝 |

### 候补调度（操作系统调度理论迁移）

| 技术 | 说明 |
|---|---|
| 三档候补策略 | `strict`（队首阻塞，作对照组）/ `executable`（默认）/ `weighted`（老化加权） |
| 可执行递补 | 按（优先级降序，编号升序）扫描队列，**暂跳**暂时不可执行的候选并保留原序号——突破 FIFO 队首阻塞，等待冲突解除后按原序获得名额 |
| 老化加权评分 | score = 1000×优先级 + 200×(信用−5) + 60×log₂(1+等待小时)——等待每翻倍 +60 分消除同档饿死；管理员不被老化越级 |
| HELD 限时保留 | `--hold-window` 下递补先落 HELD 态并写保留截止，用户截止前确认转正，超时由扫描器回收并重新递补 |
| 优先级抢占 | 管理员满员时可抢占未签到且优先级更低者，同事务补偿 +1 信用并通知被抢占者 |
| 知情候补 | 转正概率按 5 周同星期经验分布估算，候补决策从盲目排队升级为知情选择 |

### 公平治理

| 技术 | 说明 |
|---|---|
| Jain 公平指数 | 全站分配公平性量化——(Σx)²/(n·Σx²)，x 为窗口内用户获得预约数；管理端可按 1–90 天窗口审计 |
| 信用账户 | 签到/被抢占补偿 +1、爽约额外 −1、每周回补至基准 5、余额为零拒绝新预约——全部变动记流水 |
| 滑动窗口爽约限制 | 近 7 天爽约 ≥2 次限制新预约，窗口滑动自动恢复 |

### 性能工程

| 技术 | 说明 |
|---|---|
| 线程连接复用 + 语句 LRU 缓存 | 单变量对照实验：读吞吐 304→1,948 rps（**+541%**），p50 63.9→8.2ms（**−87%**） |
| N+1 查询消除 | GROUP BY 预聚合替代逐行子查询：约束感知建议端点 118→179 QPS（**+51%**，行为等价由断言逐值对拍证明）；公平审计 7 子查询/用户 → 6 条预聚合 |

### 安全工程

| 技术 | 说明 |
|---|---|
| Argon2id + 哑哈希 | 有效/无效账号同样执行哈希，账号枚举时序差压缩到约 3%（计时旁路实验实证） |
| 登录防爆破锁定 | 同一用户名连续失败达阈值（默认 5 次）锁定 900 秒，期间正确口令同样 429 |
| 三重请求校验 | CSRF Token（表单/请求双轨）+ Origin 严格同源 + Host 白名单 |
| 严格 CSP | `default-src 'self'` 下全站**零内联脚本/样式**（前端门禁静态断言） |
| 凭据生命周期 | 停用/改密/重置密码在同一事务内吊销全部 API 令牌；令牌服务端仅存哈希、明文一次性展示 |
| 每用户令牌桶限流 | 写操作突发 30、每秒补充 1，超限 429 |

### 可靠性工程

| 技术 | 说明 |
|---|---|
| outbox 通知派发 | 渠道函数指针表 + 文件渠道（JSONL）；业务事务内同写 outbox 快照，扫描期派发、失败记账可重试且不外泄错误到业务事务 |

| schema 版本化幂等迁移 | 按列存在性检测逐版本升级，只加列不重建表；构造旧库实测升级路径 |
| 存储配置 | WAL + `synchronous=FULL` + 外键约束 + `busy_timeout`——掉电安全与并发读兼得 |

### 可观测性

## 创新点

**（1）单写者事务下的规则组合语义工程化**
容量、审批、候补、抢占、信用、资源维护、周配额等多条业务规则的交叉作用，被显式归纳为五条组合语义基准（契约文档「语义澄清」节），并以五组跨规则组合断言（T63–T67）钉死唯一正确答案——例如"待审批预约不占容量但批准时重校""候补递补作为系统行为不经过审批"，解决了规则叠加场景下系统行为不可预期的工程难题。

**（2）可执行候补策略与老化加权**
突破传统 FIFO 的队首阻塞：递补事务按（优先级降序，编号升序）扫描并暂跳暂时不可执行的候选、保留其序号，配合 HELD 限时保留与优先级抢占/信用补偿闭环；进一步把**操作系统调度的老化思想**迁移为加权评分档（优先级 1000 / 信用 200 / 等待对数 60 的量纲设计），并以 Jain 公平指数与等待时长构成三策略×四档负载的量化评估——对照实验显示严格 FIFO 在队首冲突时空置率 100%，可执行与加权档均能满额递补，加权档平均等待时长**减半**。

**（3）约束感知替代建议**
只读端点按申请人当前的配额、信用、时间冲突与场次余位，逐场次解释"可预约/可候补"及不可行原因（满员、配额、冲突等），并附历史转正概率——将候补决策从盲目排队升级为知情选择；评估与提交分离，不削弱事务内全量校验的正确性兜底。

**（4）测试方法论：差分属性测试 + 故障注入 + 三方交叉校对**
weighted 递补策略以 12 组随机场景与独立 Python 参考模型**逐位对拍**（T74）；三类确定性崩溃点注入验证崩溃恢复；论文×手册×代码三方交叉校对曾抓出论文自身表格与正文矛盾的数据错误——"全部结论来自可重复执行的自动化实验"。

## 系统架构

```
浏览器（原生 HTML/JS/CSS · ui.js 基座 + theme.js 深色主题）
   │  JSON over HTTP（回环地址 127.0.0.1）
   ▼
CivetWeb HTTP 服务（8 工作线程 · #gate 认证门 · CSRF/Origin/Host · 限流）
   ▼
业务层 service.c（通知渠道+outbox · 会话/用户/扫描）+ booking.c（预约/候补/审批）
   │         asset.c（资源/时段/维护） stats.c（统计/导出） token.c（令牌/信用）
   │         ratelimit.c（令牌桶）   metrics.c（计数+延迟直方图）   log.c（分级+轮转）
   ▼
数据访问 db.c（参数绑定 · 语句 LRU 缓存 · 线程连接复用 · schema v5 幂等迁移）
   ▼
```
